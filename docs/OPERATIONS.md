## 4. Sign-in and allowlist

- Sign-in screen: index.html. It calls `CH_AUTH.signIn(email, password)` (app/ch-auth.js:198). Supabase Auth checks the password.
- Sync mode is `on` only on exactly cscdashboard.netlify.app and only when signed in. Every other host is `off`. (app/ch-auth.js:70-95; `_isNetlifyHost` :70, `backendMode` :82)
- Server check: every kv-sync and pdf-sync request must carry a valid Supabase token (checked against Supabase JWKS).
  The email in the token must be in env var AUTHORIZED_USERS (comma-separated list). (kv-sync.js:134-163, 125-129)
- To add or remove a user: change AUTHORIZED_USERS in Netlify site settings, then redeploy.
- Demo login is off on the sync host. The button is hidden and `loginDemo()` returns at once. (index.html:1188-1190, 1241-1243)
- Startup: app/db.js waits for the first token refresh, `CH_AUTH.ready()`, for at most 8 s (`_authReady`, db.js:2051-2059)
  before its first server request, so a stored token that already expired is never sent. A slower refresh does not block
  loading from the local copy.
- The ONE rule for a server answer of 401/403 is `CH_AUTH.withAuthRetry` (app/ch-auth.js:327; `_onServerRefusal` :297):
  401 = refresh the token once and send the same request again; a second 401, or any 403, ends the session (sync off,
  signed-out bar, every timer quiet). A refresh that comes back as a different user never retries the request. The
  remote-change check, the data queue drain, the live write and the PDF queue drain all go through it.
- A failed token refresh (app/ch-auth.js `_startRefresh`, rule `_refreshRefused`) ends the session only when Supabase
  REFUSED the refresh token: HTTP 400, 401 or 403. A network error or a 5xx (Supabase paused) keeps the session; the
  5-minute timer, or the next 401 on a request, tries again. How to check: with the network off, the signed-out bar
  must not appear; the offline banner does.
- Closing the browser signs the user out (2026-10-07; app/ch-auth.js `_store`, `_askPeers`, `_acceptPeerSession`,
  `_withRefreshLock`). The session `ch_sb_session` (access + refresh token) lives in per-tab sessionStorage, never
  localStorage. A reload keeps it. A new tab has none, so it asks the open tabs over BroadcastChannel `ch_auth` (message
  `need`; a signed-in tab answers `session`) and waits at most 400 ms (`CH_AUTH.settled()`; index.html and app/core.js wait
  for it before they choose between the app and the sign-in screen). No answer = signed out. Every sign-in, refresh and
  sign-out is broadcast (`session` / `signout`), so a sign-out in one tab signs out all tabs, and a different user
  signing in on one tab is followed by the others. Only one tab refreshes at a time (`navigator.locks`
  `ch_auth_refresh`); a tab that waited for the lock uses the session a peer already refreshed and makes no token call.
  A refused refresh first asks the peers once (400 ms) for a newer session before the tab signs out. Needs no env var.
  An old localStorage `ch_sb_session` is deleted at load and never used, so each user signs in once after this release.
  The offline queue (`ch_sync_queue`, IndexedDB), the per-user cache, `ch_last_user` and `ch_local_identity` are NOT
  touched on close: signed out = sync off, queued edits wait; the same user signing in again sends them once; a
  different user never sends them (`_entryBelongsTo`). Do not add any clear on pagehide/beforeunload. Limits: if the
  browser restores tabs on start (Chrome "Continue where you left off", Ctrl+Shift+T, Edge restore) it restores
  sessionStorage too and the user stays signed in; page code cannot stop that. The server-side refresh token stays valid
  until sign-out or revoke (Supabase Free has no inactivity limit; not checked in the dashboard); the client now keeps it
  only while a tab is open. How to check: node test-sync-golive-blockers.js ("8a:" to "8l:" tests); in DevTools
  Application, `ch_sb_session` is under Session Storage and absent from Local Storage; close all windows, open the site:
  the sign-in screen shows.
- A token refresh result belongs to the session it started from (app/ch-auth.js `_refresh`; the one check is
  `_sameStoredSession`: same user id and same refresh token in storage). The tab's session `ch_sb_session` is kept equal to
  the other tabs' by the broadcasts above. After the Supabase answer it is read again. If another tab changed it meanwhile (a different user signed
  in, or signed out) the result is dropped: nothing is saved, nothing is applied, and this tab follows the stored session
  (`chAuthStateChanged` fires, db.js bumps its identity epoch). A REFUSED refresh (400/401/403) also ends only the session
  it was for; a session another tab stored meanwhile is kept. How to check: node test-sync-golive-blockers.js, the four
  "7a:" tests (real ch-auth.js with a held token request).
- A 401 on a data write or on the queue drain: one token refresh, then the same request again (`CH_AUTH.withAuthRetry`,
  called from `_putWithAuth` in app/db.js, the one place a refused write is reported). The "server refused this sign-in"
  bar (`dbAuthRejected`) shows only when the final answer is still 401/403 and the session ended. If the refresh could not
  reach Supabase, the session is kept, the offline banner shows, and the write stays queued for the next drain.
  How to check: in DevTools Network, a PUT answered 401 is followed by a `/auth/v1/token` call and a second PUT (200);
  no red bar appears.

## 6. Sync write rules (app/db.js)

- A `DB.set` sends a PUT only when the canonical hash of the value differs from the hash stamped at the last sync
  (`_valueChanged`, one rule). Opening a pane or loading a page with no edit sends nothing.
- One PUT in flight per key (`_replicateWrite`). A write that arrives while one is in flight waits and is sent after
  the answer; the newest waiting value wins. Two PUTs for one key never overlap.
- How to check: open the browser DevTools Network tab on the sync host, filter `kv-sync`, reload the page and open the
  Building Performance and Savings Projection panes. Expected: zero PUT requests.
- Nothing is saved without a user edit: project progress is computed on read (app/core.js `projectProgress`, never
  stored on the Dashboard tab); recurring-meeting agendas and their tasks get ids from the project id and meeting date
  (app/csv-import.js `stableNumericId`), so two browsers generate one identical record; the Building Performance and
  Savings Projection panes save only from their inputs and buttons (`bpSave`, `bspSave`), never on open, and
  `getBspCfg` is the one reader of the Savings Projection settings with defaults. How to check: open a project
  Dashboard tab and both panes with the Network tab filtered on `kv-sync`: zero PUT.
  Same rule for zoom: opening the Equipment Matrix only reads `en_em_zoom` and paints it (`emApplyZoom`, app/equipment-matrix.js);
  only the zoom buttons save (`emSetZoom`). `setTableZoom` (app/site-functions.js) saves to local storage only on a click, not on a re-apply.
  Theme: `ch_theme` stays a raw local key, never sent to the server. On a user switch app/db.js `_clearPerUserLocalState(prevUid, nextUid)`
  parks it under the local key `ch_theme_user::<userId>` (never in a backup: `isNeverBackupKey` lists the prefix) and puts back the next user's own value, so A keeps Light after A->B->A and B
  does not get A's theme. How to check: node test-sync-golive-blockers.js (theme test), node test-em-zoom-no-write-on-open.js.
  Table prefs: the Cost Estimate table keeps column widths, hidden columns and a schema marker in `ch_tbl_*_pricing_tbl_<projectId>` (app/pricing-estimator.js).
  Render never writes them: `_pricingMigrateColSchema` returns when nothing is stored; `_pricingSetColWidths`/`_pricingSetHiddenCols` (user resize/hide/show only) also stamp the schema marker.
  How to check: node test-pricing-tblprefs-no-write-on-render.js (6 pass); Network tab, filter `kv-sync`, open JOCO Cost Estimate: zero PUT.
  Phase over allowance is a data notice: `console.warn` (not error) in `_pricingComputeRecommendedTimeline`.
- Version stamps are one local record per key, `ch_rv::<key>` = `{ stamp: {version, hash}, base? }` (app/db.js
  `_persistStamp`, the one writer; `_setSynced` the one stamper). A tab writes only the record of the key it synced, so a
  second tab can never overwrite the first tab's stamps (the old whole-map `ch_replica_state`/`ch_sync_base` are split once
  on the first load and removed). These records never sync and are never in a backup (the one prefix is `SyncClassification.RV_PREFIX`; `isNeverBackupKey` covers it for `siteBackup` and `RestoreMerge.isEngineKey`).
  How to check: DevTools, Application, IndexedDB, CompanyHub store: keys `ch_rv::en_projects` etc.; no `ch_replica_state`.
- Auth/session keys (`ch_sb_session`, the refresh token) are never in a backup file and a restore never writes them. The one
  list is the `neverBackup` entries of `PER_USER_CH_ENGINE_EXCLUSIONS` (app/sync-classification.js), read through
  `SyncClassification.isNeverBackupKey`. `siteBackup` (app/site-functions.js) drops them and `RestoreMerge.isEngineKey`
  (app/restore-merge.js) skips them. How to check: node test-sync-golive-blockers.js, the "(e):" test; open a new backup
  file and search for `ch_sb_session`: no match.
- Queue entries with no owner tag (saved by v2026.10.06.83 or older) are never sent (`_retireOwnerlessEntries`, runs when
  the queue loads). Each goes to Conflict history as `queue-entry-no-owner` with its value, leaves the queue, and its
  version stamp is dropped so the next load compares the local copy with the server. How to check: after one load the
  "N unsynced changes" bar is gone and Sync status, Conflict history lists the entries.
- Conflict history (`en_conflict_archive`, local only) is one list per browser. Every entry carries an owner tag
  (`_appendConflictArchive`, same shape as a queue entry; it stores a COPY of the losing value, so the merge that follows cannot change an archived version). The one visibility rule is `_archiveEntryVisible`, applied by
  `DB.getConflictArchive` (the one reader: the viewer, the export button and Reset all call it): an entry for a shared
  key is shown to everyone on this browser; an entry for a per-user key (`ch_*` prefs, zoom levels) only to its owner.
  Another user's per-user entry, or one saved by a build before owner tags, stays in storage, is never shown and is never
  removed by this user (`clearConflictArchive` removes only entries the user can see). app/sync-ui.js redraws the link and
  closes the panel on `chAuthStateChanged`. How to check: node test-sync-golive-blockers.js, the "7c:" tests.
  Reset (`siteResetData`, site-functions.js) exports only the entries this user can see (`DB.getConflictArchive`), never
  another user's. The wipe KEEPS the entries this user cannot see (`DB.getConflictArchiveOthers`, written back after
  `DB.clear()`): they are neither exported nor deleted. The backup (`DB.getAllForExport`, then `siteBackup`) holds the same
  visible list only, and never `ch_sync_queue` (unsent edits may belong to another user). An old per-user queue entry with no
  owner tag is archived with NO owner (`_retireOwnerlessEntries`): shown to nobody, never sent, kept. How to check:
  node test-sync-golive-blockers.js, the "F2/F3:" and "F4:" tests.
- Identity guards on the write path (app/db.js). `_sendKvPut` is the ONE sender: if the edit's owner id is not the signed-in
  user at send time it returns `stale-identity` (no PUT, no stamp), so a value waiting behind another PUT or a hash check is
  never sent with the next user's token or key. A successful live write (`_writeOne`) removes older queued entries for the
  same key and owner, so the drain cannot replay an old value. A per-user edit whose author signs out while it is in flight (`stale-identity` in `_writeOne`, app/db.js) is queued under the AUTHOR's id (`payload.owner`), never sent as another user, and drains when that author signs in again. A live server row with no value (or null) is unreadable:
  `_reconcileIncoming` keeps the local copy and its stamp and raises `dbHydrateFailed`. `_reconcileIncoming` also returns without applying when the local value changed, or a write got queued, during its hash await: an edit made in that gap is never replaced (test REV3). A refusal (403 or second 401) in a
  tab whose cached user differs from the stored session takes over the stored session (`_onServerRefusal`), it never clears
  it. How to check: node test-sync-golive-blockers.js, the "F1:", "F5:", "F6:" and "later successful write" tests.
- Savings %: `getBspCfg` (app/utility-data.js) is the ONE reader of a building's `savingsPct` (default 11, a stored 0 stays 0).
  utility-data.js, report-engine.js and graphics-setpoints.js all call it.
- Local per-user stores on a shared browser (app/db.js). The one "a write for this key is still waiting" rule is
  `_hasQueuedWrite` (hydration skip, first-connect upload skip, `_valueChanged`): a queued entry counts for a shared key
  whoever owns it (same server row), and for a per-user key only when it is the signed-in user's own (`_entryBelongsTo`),
  so another user's queued pref never blocks this user's own row from loading. On an identity change
  (`_clearPerUserLocalState`, live or hard refresh) the per-user cache values, raw localStorage prefs, AND every per-user
  version stamp `ch_rv::<key>` (also one with no cached value) are removed; queue entries are never deleted. Merge bases
  and `ch_deleted_items` hold collection keys only (shared). `ch_last_user` holds the last user's id and email (the
  "N unsynced changes by <email>" bar reads it). How to check: node test-sync-golive-blockers.js, the "7d:" tests.
- The auth session `ch_sb_session` (access and refresh tokens, app/ch-auth.js) is classified local-only at the one place
  that decides what syncs (app/sync-classification.js `PER_USER_CH_ENGINE_EXCLUSIONS`). It never gets a wire key, is never
  uploaded by the first-connect upload, and is never removed by the identity-change sweep. It is now in sessionStorage; the rule stays so a
  localStorage copy can never sync. This matters in localStorage-fallback mode (IndexedDB unavailable), where db.js loads every localStorage key into its cache. How to
  check: node test-sync-golive-blockers.js, the "(a):" test; `SyncClassification.classifyKey('ch_sb_session')` is
  `local-only`.

- Restore has 5 modes. "Merge, keep whichever copy is newer" (`'newer-wins'`) is the same as backup-wins but keeps a strictly newer server record. The next paragraph describes backup-wins.

- Restore mode "Make this backup the server copy" (`'backup-wins'`, app/restore-merge.js `mergeValue` and `plan`, dialog in
  app/site-functions.js `_restoreDialog`). It reuses `_restoreApply` and `DB.restorePush` (no second upload path): a key that
  is absent on the server is inserted at version 1 (`baseVersion` null); a key that differs is replaced at the server version
  just read, with `explicitOverwrite`, so kv-sync.js keeps the old copy in `kv_history` (20 per key, 30 days). A key whose
  content already equals the backup is not sent. Rules: a plain key or map takes the backup value; EVERY record collection
  key (`en_projects`, `en_customers`, `en_tasks`, `en_dc_events`, `ems_leads_v1`, the audit log, report history,
  `en_utility_cust_<id>` with its buildings, meters and bills, `en_eqmatrix_cmaps_*`) is a union by id in which the BACKUP
  record wins field by field on a matched id (Matt worked only on the GitHub site since 2026-08-19, so the backup is newer);
  records only the server holds are kept, never deleted. The one exception is `en_presented_savings` (frozen client figures):
  add-only. The old server copy of every changed key stays in `kv_history`. legacy `en_utility_<id>` keys are
  skipped; nothing is deleted; a tombstoned key stays deleted unless ticked; a per-user key goes only to the signed-in user
  (`DB.restoreScope`). A key that would still remove records (a plain key whose nested lists lose items) is HELD: listed with
  the count, unticked, not sent until the user ticks it (`opts.allowRemoval`, `item.held`). After the apply the dialog shows
  one row per key: OK with the action ("inserted as v1", "overwrote vN with vN+1, old copy kept in history"), Failed with the
  HTTP status (`DB.restorePush` returns `httpStatus`: 409 for a conflict, the server code otherwise), Skipped or Not sent with
  the reason. A second run with the same file finds server = backup and sends nothing. How to check:
  node test-restore-merge.js ("backup-wins" tests), node test-sync-golive-blockers.js ("migration R1-R3"),

## 6d. Backup importer: scripts/migrate-seed.js (Matt runs it; agents never hold the key)

What it is: a Node script (scripts/migrate-seed.js) that loads a backup file into the Supabase `kv` table and the `pdf_blobs`
bucket. It talks to Supabase directly, so it costs 0 Netlify credits and works while Netlify has no deploy credits.
The old whole-key `--force`, `--live` and `--dry-run` flags are gone. Merge rule: it calls `RestoreMerge.mergeValue(key,
server, backup, 'newer-wins')` (app/restore-merge.js), the same function as Restore "Merge, keep whichever copy is newer". A
record only on the server stays. A record in both is replaced by the backup record whole in the importer only (it passes `{ replaceWhole: true }` as the sixth argument of `mergeValue`; app Restore does not, and keeps every field the backup lacks) (a field only the server record has, such as a stale `updatedAt`, is dropped; the nested list and the derived meter cache fields are kept; the old value goes to `kv_history`; the dry run counts it as changed and the diff file names the lost fields). On top: a backup record is dropped when the server
copy has a strictly newer `updatedAt`/`updated_at`/`modifiedAt`/`lastModified`. No timestamp = the backup wins. This
"newer wins" rule lives INSIDE `mergeValue` (app/restore-merge.js, `recordTime`/`curIsNewer`, 'newer-wins' mode only; 'backup-wins' is an unconditional overwrite that lists the newer server records it overwrites). It runs at
every level (building, meter, bill, pricing entry, plain-key object). The app Restore "Merge, keep whichever copy is newer" uses the
same function, so the app and the importer give the same result, except that the importer replaces a matched record whole. A key is HELD (no write, listed in the diff file) when the
server has a whole item the backup lacks: a list item, a map entry, or a plain field of any type in a plain-key object. A field lost inside a matched record is not a hold (see above). Name a held key in `--allow-removal`
to write it.

Modes:
- Default = dry run. No write. Console shows counts only (keys and records: new / changed / server-only / identical). The full
  diff (record ids, every record the backup overwrites) goes to `<report-dir>/YYYY-MM-DD-HHMM-supabase-import-diff.json`
  (default `AI/_context/live-data/diffs/`). The diff names nested records (level + id path), the field names that change, are
  added or are lost, and why a key is held. Field names only, never values. The script refuses any report or snapshot folder inside the repo.
- Server for the diff: `--server-file <image.json>` (offline, no key) or `--target prod|staging` (GET only).
- `--apply --target prod|staging` writes. Order: read server rows, save them to
  `AI/_context/live-data/snapshots/YYYY-MM-DD-HHMM-supabase-snapshot.json` (stop if that fails), then per key one `kv_history`
  row (the old server row) and a version-checked PATCH (a key that changed on the server meanwhile is reported as a conflict,
  never overwritten), then new keys at version 1, then PDFs (write-once, same-hash re-run is a no-op).
- Target safety. Needs ONLY the target-specific values: URL = env `SUPABASE_URL_PROD` or `SUPABASE_URL_STAGING`; key = env
  `SUPABASE_SECRET_KEY_PROD` / `SUPABASE_SECRET_KEY_STAGING`, else the Windows Credential Manager generic credential
  `companyhub-supabase-<target>-key`. The generic `SUPABASE_URL` and `SUPABASE_SECRET_KEY` are NEVER read. There is no `--url` and no
  `--cred-target`. A missing value stops the run (resolveCreds, scripts/migrate-seed.js). A URL ending in `/rest/v1/` is cut to the bare origin (normalizeSupabaseUrl). The PDF stat treats HTTP 404, and HTTP 400 with a Storage body of statusCode 404 (NoSuchKey), as missing; any other 400 stops the run (pdfStorageStat). The log prints the target name and the host
  (`Server: WRITING to target=prod host=<host>`), never the key. No prompt. The key is never printed or stored.
- `kv_history` rows written here are not trimmed (kv-sync.js trims on its own writes: 20 rows or 30 days a key).
- Failed writes (applyPlan, applyPdfFiles, fetchWithRetry, scripts/migrate-seed.js). Each kv, kv_history and PDF write is tried up to 4 times (RETRY.attempts) with 1 s, 2 s, 4 s waits and a 180 s timeout per try. The same timeout and retry apply to the reads (kv row read, key list, Storage stat and download), so a hung read cannot stop the run silently. Retried: a network error, a timeout, HTTP 408, 429, 500, 502, 503, 504 and 520-524 (isRetryableStatus). Any other status (a 4xx, 501, 505) is not retried. A retry that gets 409 with the same hash on the server counts as inserted (the first try wrote the row and lost the answer); if the re-read itself fails, the FAILED line says so. A PATCH that matches 0 rows, or gets a 2xx answer that is not JSON, reads the key: the same hash on the server counts as updated (patchKvRow); a different hash is `conflict-version-changed`. The history snapshot is idempotent: before the write and before every retry the importer looks for a kv_history row with the same key and version (historyRowExists) and writes none if one exists, so a lost answer or a re-run after a failed PATCH adds no duplicate row. kv_history has no unique constraint; no schema change was made. A write that still fails is listed by name: `FAILED key <key> status=error http=<status> reason=<server message>` (or `FAILED pdf <canonical key> ...`). The key name and a shortened server error are printed (scrubServerText: the error code and the first 80 characters of the message). The secret key is never printed. A server error can quote a fragment of the row, so the cut is to 80 characters; it is not a guarantee that no data text can appear. Conflicts and history failures are listed too. If N > 0 the last line is `APPLY INCOMPLETE: N failed` and the process exits with code 1; `APPLY COMPLETE` prints only when 0 failed. If keys were HELD (not written) the last line is `APPLY COMPLETE WITH N HELD key(s) NOT WRITTEN` and the re-run will still show them as changed. Run the same command again: it writes only what is missing. A kv value over KV_VALUE_MAX_BYTES (25 MiB of JSON) is shown as `OVERSIZE` in the dry run and is not sent by --apply (it fails by name). That limit is an importer guard, not a Supabase number: the largest value proven to write is the 9 MB Equipment Matrix key. The app reads and writes that value through netlify/functions/kv-sync.js, which gzips bodies to stay under Netlify's ~6 MB function cap (comments at kv-sync.js:44-48 and 178-181, measured 2026-07-19: 9.03 MB to about 0.35 MB), so a large importer value does not need a smaller limit for the app. An empty backup value (`empty-skipped`) adds 0 to the record counts.

## Baseline rates are usage-weighted; mismatched bills are left out (2026-10-13)

- Browser only. No schedule, no timer, no env var, no server call. Cost: about 0.7 ms per `computeSeasonalBldgRates` call (runs the flag engine once per meter, no cache); `getProjMatrixSavingsTotal` for all 5 projects 48 ms on the 2026-10-12 backup.
- Method (`computeSeasonalBldgRates`, computations/rates.js): every derived baseline rate (kWh, kW, therm, gallon, water, sewer, stormwater; per season, per calendar month, annual) = sum of the charges / sum of the usage over the bills in that bucket. It is NOT the mean of per-bill rates. Charge and usage of one bill come from `getBillRateParts(bill, type)` (rates.js), the same function `getStoredRate` and `getStoredKwRate` divide. A straddling Evergy bill with printed split lines gives each season its line rate weighted by that line quantity (`_billSeasonRates` returns `summerQty` / `winterQty`: kWh of the lines, or kW = charge / rate). A straddling bill without split lines gives its usage prorated by its days in each season. A bill with a stored rate but no cost or no usage has no weight and gives nothing. Stormwater has no usage: each bill counts once, so its rate is the mean monthly charge.
- Bills left out: `computeMeterRateExclusions(meter, building)` (computations/bill-flags.js) is the ONE predicate. It returns the baseline-bill ids that `computeMeterFlagSummary` flags with a rule in `BILL_RATE_EXCLUDE_RULES` = `charge_vs_usage` (total vs usage x the meter's usual rate, 3x) or `usage_charge_mismatch` (water and sewer usage charge vs usage, 2x). The thresholds stay in `BILL_FLAG_THRESHOLDS`. A flag the user dismissed does not exclude. The flags use ALL bills of the meter for the usual rate, so a short baseline does not change them. Bill data is never changed. No new per-commodity $/unit check was added: on the 2026-10-12 backup these two rules already flag the water and sewer bills with a wrong usage (one with usage 291 for $313, one with usage 4,303,400 gal for $700).
- `computeSeasonalBldgRates(...).excluded` lists the left-out bills: `{ meterId, commodity, billId, start, end, ym, usage, charge, rules, reason }` (one per bill that would have fed a rate). `formatExcludedBillsLabel(excluded)` (rates.js) writes "2 bills excluded: Nov 2025, Dec 2025". Utility Data > Baseline stat pills show it as a "Left out of the rates above" pill next to the rates (`_udBaselineRatePills`, both pill strips in app/utility-data.js).
- Effect on the 2026-10-12 backup: sewer and water rates fall from a 10x-too-high value to about $0.01 per gal; electric kWh and kW rates move by under 1.5% on the buildings checked; a gas annual $/therm rate rises 8% to 28% where usage is winter-heavy (weighted by therms), and the month-by-month gas array does not change when each month has one bill. Project Performance is identical before and after; the Energy Savings matrix total moves under 0.1%.
- Gate: `node tools/gate-single-rate-source.js` fails on any read of a measure's `.rates` (also destructured `rates`, `['rates']`, `'rates'` name) outside `measureRatesNow`, `writeRateSet` and `writeRateField`. A read that is not pricing is marked `// rates-ok`.
- Check: `node tools/test-rate-usage-weighted.js` (30 checks, synthetic); `node tools/test-utility-seasons.js`; `node tools/test-bill-flag-rules.js`; `node tools/gate-single-rate-source.js`. The list of excluded bills on a local backup: run `computeSeasonalBldgRates(projId, bldgId, meterId).excluded` for every meter.
- Month rate (2026-10-13): savings per meter per calendar month use that month's own bill rate. When a month holds several bills, `getMonthBillRate(bills, type)` (computations/rates.js, type kwh, kw or gas) returns sum of charges / sum of usage from `getBillRateParts`; it is not the mean of the per-bill rates. A bill with no charge or no usage is left out; with none computable the first bill's stored rate is used. Callers: `getMeterSavings` (computations/savings.js, electric kWh, kW and gas) and the Meter Performance demand and gas cost maps (app/utility-data.js, `perfDemByYm`, `gasCostByYm`). `tools/gate-single-rate-source.js` fails on a `.reduce(... + rate ...) / rates.length` mean. ## Physics constants and the one fan power rule (2026-10-13, branch 2026-10-13-phase2-fan-affinity-constants)
- ONE home: `computations/physics.js` (loaded first of the computations files in energy-department.html). No schedule, no env var, no host behavior. Three base figures, every other factor is derived from one of them: `BTU_PER_KWH` 3412.14 (EIA), `BTU_PER_GAL_PROPANE` 91452 (EIA), `BTU_PER_HR_PER_BHP` 33475 (boiler horsepower); plus `BTU_PER_THERM` 100000, `KW_PER_HP` 0.746, `FAN_AFFINITY_EXPONENT` 3. Sources: https://www.eia.gov/energyexplained/units-and-calculators/british-thermal-units.php. Functions: `hpToKw`, `fanPowerFraction`, `ductStaticResetPowerSavings`.
- Propane is ONE figure (2026-10-13, Matt decision): 91,452 Btu per gallon (EIA). Bill conversion (gallons to therms, 0.91452) and the EUI factor (91.452 kBtu per gallon) both come from `BTU_PER_GAL_PROPANE`. They were 0.9153 and 91.5 (two sources). - Fan rule: power fraction = fixedShare + (1 - fixedShare) x max(speed, minSpeed) ^ exponent. Defaults: exponent 3, minSpeed 0, fixedShare 0 (ideal cube law). Every caller used the pure cube law with no floor, so no value changed. Callers: `vfd_savings`, `pump_vfd`, `vav_reheat`, `fan_wall` (app/ecm-calculators.js) and the duct static pressure reset estimate in BAS Trends (`btEstimateSavings`, app/bas-trends.js). Duct static reset: speed = sqrt(1 - pressure reduction), saving = 1 - fanPowerFraction(speed). A 20 percent pressure cut saves 28.4 percent of fan power with no fixed losses (the audit text said 49 percent; the code gives 28 percent). The fan model and the BAS report use a 10 percent fixed-loss share (`FAN_FIXED_POWER_SHARE`): 25.6 percent, ONE answer through `fanResetSavingsFraction(0.2)` (computations/fan-savings.js). 2026-10-14 review fixes: `fanPowerFraction` takes `opts.curve`: 'affinity' (default, as above) or 'ashraeG', the ASHRAE 90.1 Appendix G part-load fan power curve of a variable-air-volume fan with a drive and fixed duct static pressure: 0.0013 + 0.1470 x PLR + 0.9506 x PLR^2 - 0.0998 x PLR^3 (`FAN_CURVE_ASHRAE_G`; source: NREL openstudio-standards, lib/openstudio-standards/hvac/components/fan.rb, `fan_variable_volume_set_control_type`, 'Multi Zone VAV with Fixed Static Pressure Setpoint', Appendix G baseline of ANSI/ASHRAE/IES 90.1-2016, read 2026-10-14). The fan model default is 'ashraeG' (`FAN_DEFAULT_PART_LOAD_CURVE`): its power is at or above the affinity curve with 10 percent fixed share from 30 to 99 percent flow, so it gives the lower savings. ### Fan end use and the Fan Savings template (2026-10-14, phase 6)
- What it is: `getEndUse(projId, bldgId, 'fans')` (computations/end-use.js `_fanEndUse`) answers the building's supply-fan kWh from its Equipment Matrix rows (equipment types ahu, rtu, doas, mau, fan that have a fan point: a supply fan status, speed, amps or airflow point, a High/Low enable pair, or any point named "fan" (`_fanRowHasFanPoint`); duct, damper, water detection and zone sensor rows of an AHU are not fans; the rows of the building by `_emNormBldgNameForJoin`). It has the same shape as every other end use, with `source: 'matrix'`, plus `units` (one model per row), `capFactor`, `capAnnual` and `levels`. It runs when a template opens or calculates; no timer, no network, no new storage key.
- Unit model: ONE function, `fanUnitModel` (computations/fan-savings.js). Fan kW: trend running amps (else the matrix amps point, else the amps field) x the voltage and phase asset fields (`motorKwFromAmps`, physics.js), else supply fan airflow x W per cfm (`fanKwFromCfm`; `FAN_W_PER_CFM` low 0.774, mid 0.851, high 0.928; mid is used), else horsepower (the Horsepower/Tons column is read as HP for ahu, doas and mau only; motor efficiency 0.9, load 0.8), else amps with an ASSUMED 208 V three phase (the low end of common supply voltages, so a missing voltage never overstates; labelled default). A unit with none of these gets a stated Default estimate from `fanModelUnits` (computations/fan-savings.js), the first rule that applies: (a) the median kW of the sized units of the same equipment type in the same building, (b) the same type across the other buildings of the project, (c) NOT available: the Equipment Matrix has no link from a VAV box to its AHU, (d) the national average ventilation share of the building's TOTAL baseline electricity (`fanVentilationShare` and table `FAN_VENTILATION_SHARE_CBECS`, computations/physics.js; source EIA CBECS 2018 Table E5, https://www.eia.gov/consumption/commercial/data/2018/ce/xls/e5.xlsx, billion kWh: Education ventilation 19 of 128 total = 14.8 percent, used when the building's own type, else (when the building has none) the project type, names a school; the label says which type was used; All buildings 213 of 1,196 = 17.8 percent, used otherwise), less the fans already sized, split across the units still unsized by tons when the matrix row has them (a unit without tons takes the mean of the others), else equally (kWh per sq ft shown; label "Default: national average ventilation share for <type> buildings (EIA CBECS 2018)"). Each is tagged Default with its basis in `kwHow`; the unit model carries `estimate` ('sibling', 'project', 'area'). With no sibling and no total baseline electricity the unit stays not sized and the template says why. Run hours: BAS trend run hours (fan status, else High/Low enable, else amps, else speed) x 365; else a matrix read with the fan on while the schedule point says unoccupied (8,760 h); else 3,640 h. Speed drive: a speed trend that moves means a drive; else the unit field Has variable speed (yes/no/unknown; Equipment Matrix column `hasVfd`, stored once in `data.edits['<rowId>::hasVfd']` by `emSetAssetEdit`, app/equipment-matrix.js, and set per unit in the template picker); else any point of the unit named like a drive is evidence of a drive: `fanDrivePointName` (computations/fan-savings.js, the one rule) takes the first point name with VFD, VSD, Drive, Inverter, Hz, Frequency or Speed, except a High/Low speed enable, wind or air speed, a diagnostic, an energy recovery wheel, and a point of another fan (exhaust, return, relief, condenser, compressor, pump); the model says "Drive found from point: <point name>" (data level: Equipment Matrix), and Has variable speed = No set by the user wins over it. No evidence means the drive status is UNKNOWN (not assumed constant speed). `driveStatus`: 'has', 'none' (Has variable speed: No, or a speed trend that stays in one range) or 'unknown'. A unit with a drive and no moving speed trend has no speed profile and counts at its full-speed power (a speed trend that moves gives the profile and the part-load power). Unit fields (voltage, phase, amps, HP, Has variable speed) are read from `data.edits` of the matrix record (an earlier read of the key `en_eqmatrix_edits_<projId>` missed every user edit). Two-speed fan: a High/Low enable trend, or both enable point names in the matrix row; Low share from the enable hours, else 55%. Every value carries a data level: `trend` (measured trend), `matrix` (Equipment Matrix value) or `default` (stated assumption, constants at the top of fan-savings.js). A better level replaces a worse one on its own when data arrives.
- Cap and months: fans run all year, so their energy sits in the bills' baseload, not in the HVAC electric above baseload. The sum of the sized units is capped by the building's total baseline electricity (`_euTotalElectric`, computations/end-use.js, the HVAC Load Estimate `totalKwh`) less its measured cooling and electric heating end uses: `capFactor = cap / sum` when the sum is larger, else 1; with no total there is no cap and the label says so. Double-count rule: `getEndUse(.., 'nonHvacElectric')` is that same remainder LESS the fans (annual, 12 months and kW series, never below 0; its source label says so), so cooling + electric heating + non-HVAC + fans never add up to more than the building total. `hvacElectric` is unchanged (cooling + electric heating). Monthly = annual x days in month / 365 (a fan runs all year), so the Energy Savings measure for a fan saving is shaped by days in month, not by cooling. The estimated units are inside the sum, so the cap applies to them too.
- Template: `ECM_TEMPLATES.fan_savings` (app/ecm-calculators.js, category HVAC Equipment). Quantities only (no cost, no payback). Inputs: the unit picker (type `fan_units`, drawn by `ecmFanUnitsFieldHtml` with the data level of each input and "what would refine this estimate"), three measure switches, the fan power curve (default ASHRAE 90.1 Appendix G), the static pressure cut (default 20 percent), and a "Size is right" tick on each unit sized by the national average. COUNTED vs POSSIBLE (2026-10-14 review fixes): a drive or a two-speed replacement is counted in `savings_kwh` (and so in Add as Measure) only when the unit's drive status is known "none"; units of unknown drive status show `possible_drive_kwh` ("Possible if no drive is installed ... confirm drive status to include") and a unit sized by the national average shows `possible_size_kwh` until its Size is right box is ticked; neither is in the total. Measures from `fanSavingsForUnits`: (a) drive or efficient motor on a constant-speed fan (fan kW x hours x the mid of a published range: `FAN_VFD_SAVINGS_RANGE` low 25, mid 35, high 45 percent, "25-45% reduction compared to constant-volume belt-drive systems" from the ASHRAE Handbook fan chapter, the PNNL plug fan study and ENERGY STAR fan guidance; the template shows low, mid and high, counts the mid; label `FAN_VFD_SAVINGS_LABEL` "Default: typical savings range for adding variable speed to a constant-volume fan, 25-45% (ASHRAE Handbook fan chapter; PNNL plug fan study)"; the drive-name rule `fanDrivePointName` also serves the Audit Estimate "Fan speed/VFD" control concept (app/audit-estimate.js), and reads camelCase and underscore keys as words; the monthly HVAC load profile `fanSpeedProfile` and the lowest airflow input were removed because no source stood under them: they gave 74 percent on one building, above published ranges; a unit with a moving speed trend already has a drive and gets no drive saving), (b) drive in place of a two-speed motor (High hours only: Low hours stay at Low speed; mean power over Low to High), (c) duct static pressure reset on a fan that has a drive (`ductStaticResetPowerSavings`; share of fans it works on: setpoint trend flat = 1, moving = 0, no trend = 70 percent). `calculateEcm(templateId, inputs, ctx)` now passes `{projId, buildingId}` to `calculate(inp, ctx)`. Add as Measure sends `savings_kwh` and `savings_kw` shaped by the fan end use (`ECM_MEASURE_FIELD_MAP.fan_savings`); dollars come from `calcMeasureDollars` at baseline-period rates. A projected estimate, never called measured or verified.
- Trend import (app/bas-trends.js): new point types `fanhienable`, `fanloenable`, `fanamps` (plus the existing `fanstatus`, `fanspeed`, `staticp`, `staticpsp`), matched by point name. `btFanPointExtras` adds small per-day numbers to the existing daily summary in `en_bas_<projId>` (run hours; amps running mean; hours and mean speed in four speed bins): no raw rows are added. MEASURED size (synthetic file, `node tools/test-fan-savings.js` section 7c): one unit, 365 days, six fan points (status, amps, speed, static setpoint, High enable, Low enable) = 376,346 characters (368 KB) of `en_bas_<projId>`. `btCheckStorageSize` counts 2 bytes per character, so one such unit-year counts 752,692 bytes and the 3 MB console warning (`btWarnIfStorageLarge`) is reached after about 4 unit-years of full fan points (about 8 by character count). `btMergeSummaries` adds a point type that an old day lacks and, on a fan point type the day already has (fanstatus, fanspeed, fanamps, fanhienable, fanloenable), the fan facts it lacks (run hours, mean amps, speed bins), so a re-import upgrades old days; it never overwrites a stored value. The trend is joined to the matrix row by building and equipment tag (normalized name). - BAS Trends report (2026-10-14 review fixes): `btEstimateSavings` (app/bas-trends.js) takes fan kW from `fanKwFromHp` (nameplate HP, motor efficiency, load 0.8), run hours from `fanDefaultRunHours` (3,640 h, was 2,400 h) and the duct static reset fraction from `fanResetSavingsFraction` (25.6 percent for a 20 percent cut, was 28.4 percent). ### Measure cost lines and ONE payback (2026-10-14, phase 7)
- What it is: each Energy Savings matrix measure holds its cost as `m.costLines` (stored with the measure in `en_projects`, `savingsData.measures`). A line is `{id, kind, label, vendor, hours, amount, note}`. Kinds: `thirdParty` (price from a third party, vendor name optional), `labor` (internal labor: hours x the hourly rate), `parts`, `incentive` (taken off the cost). The old measure fields `implCost` and `incentive` are gone (the 2026-10-12 backup held no value in them).
- Owner of the sums and the payback: `computations/cost-lines.js` (loaded by energy-department.html after fan-savings.js). `measureCostTotals(m, laborRate)`, `sumCostTotals`, `costLineAmount` and `simplePayback(gross, incentive, annual)` = (total cost - incentive) / annual savings $. It is the ONLY payback formula. `years` is null when there is no cost or no savings; 0 when the incentive is larger than the cost.
- Labor rate: the pricing estimator hourly rate, `_pricingGetConfig().hourlyRate` (app/pricing-estimator.js; default `COST_LABOR_RATE_DEFAULT` 170 $/hr; set in the Cost Estimate toolbar). `msrLaborRate()` (app/energy-savings.js) reads it when the cost is shown. A labor line stores hours only, never a rate or a dollar amount.
- Savings side: `msrAnnualSavings(projId, m)` (app/energy-savings.js) = `calcMeasureDollars` annual total at the measure rates (`measureRatesNow`). `getProjMatrixSavingsTotal` calls it. `msrCostSummary(projId, m)` (one measure) and `projCostSummary(projId, measures)` (roll-up) call `simplePayback`. The roll-up payback divides by the matrix savings of the measures that have a cost (a measure with no cost line adds savings but no cost); `annualAll` is the savings of all measures in the list.
- Where it shows: the Financials block of the measure detail on the Energy Savings tab (`msrFinancialsHtml`: lines, total cost, incentive, net cost, matrix savings, payback); the two items "Net Cost" and "Simple Payback" of the Selected Measures card (`_svCostItemsHtml`); the Cost Estimate tab roll-up table (`_pricingMeasureCostRollupHTML`, app/pricing-estimator.js, above the tier table in every estimate type) and the footer savings line (`_pricingSavingsLineHTML`). The pricing estimator does no energy math: it reads cost lines and matrix savings.
- Fan Savings: `ecmAddAsMeasure` adds `defaultCostLinesFor('fan_savings')`: one internal labor line "Reprogram BAS for variable speed" with NO hours (the labor model, `COST_PER_SEQ_HOURS_DEFAULT`, has no task for this work, so no hours are invented). The user types the hours.

- Escaping: vendor, description, note, measure name and measure notes go through `_escHtml`. The handlers read ids from data attributes (`data-proj`, `data-msr`, `data-line`), so no id is put in a script string.
