How to check that a function works:
- Netlify dashboard, site cscdashboard, Observability, then Functions. Open the function and read the invocation log.
- keepalive: look for the log line `[supabase-keepalive] OK: HTTP 200` once each day. A line with `FAIL` means a problem
  (supabase-keepalive.js:11,21,25,28).
- kv-sync and pdf-sync: a 401 means a bad token. A 403 means the email is not in AUTHORIZED_USERS. A 502 means a Supabase failure.
  (kv-sync.js:152,160; pdf-sync.js header)
- Sync PUT bodies over 1 MB are gzip. app/db.js (_maybeGzipBody) sends JSON `{"gz":"<base64 of gzip(value JSON)>"}` with content-type application/json. The runtime never sees a binary body (netlify dev and the Functions runtime broke binary bodies). kv-sync.js `getRawBody` is the one decode path: it gunzips `gz` when present, else reads plain JSON. Netlify synchronous Functions accept a request body up to 6 MB (Netlify Functions limits), so 1.8 MB of gzip (about 2.4 MB as base64) fits. A failed queue entry keeps the server's error text. Check: test-kv-sync-gzip-body.js.
- Netlify scheduled functions only run on the published (production) deploy.

## 4. Sign-in and allowlist

- Sign-in screen: index.html. It calls `CH_AUTH.signIn(email, password)` (app/ch-auth.js:198). Supabase Auth checks the password.
- Sync mode is `on` only on exactly cscdashboard.netlify.app and only when signed in. Every other host is `off`. (app/ch-auth.js:70-95; `_isNetlifyHost` :70, `backendMode` :82)
- Server check: every kv-sync and pdf-sync request must carry a valid Supabase token (checked against Supabase JWKS).
  The email in the token must be in env var AUTHORIZED_USERS (comma-separated list). (kv-sync.js:134-163, 125-129)
- To add or remove a user: change AUTHORIZED_USERS in Netlify site settings, then redeploy.
- Demo login is off on the sync host. The button is hidden and `loginDemo()` returns at once. (index.html:1188-1190, 1241-1243)
- Startup: app/db.js waits for the first token refresh, `CH_AUTH.ready()`, for at most 8 s (`_authReady`, db.js:2051-2059)
  before its first server request, so a stored token that already expired is never sent. A slower refresh does not block
  loading from the local copy.
- The ONE rule for a server answer of 401/403 is `CH_AUTH.withAuthRetry` (app/ch-auth.js:327; `_onServerRefusal` :297):
  401 = refresh the token once and send the same request again; a second 401, or any 403, ends the session (sync off,
  signed-out bar, every timer quiet). A refresh that comes back as a different user never retries the request. The
  remote-change check, the data queue drain, the live write and the PDF queue drain all go through it.
- A failed token refresh (app/ch-auth.js `_startRefresh`, rule `_refreshRefused`) ends the session only when Supabase
  REFUSED the refresh token: HTTP 400, 401 or 403. A network error or a 5xx (Supabase paused) keeps the session; the
  5-minute timer, or the next 401 on a request, tries again. How to check: with the network off, the signed-out bar
  must not appear; the offline banner does.
- Closing the browser signs the user out (2026-10-07; app/ch-auth.js `_store`, `_askPeers`, `_acceptPeerSession`,
  `_withRefreshLock`). The session `ch_sb_session` (access + refresh token) lives in per-tab sessionStorage, never
  localStorage. A reload keeps it. A new tab has none, so it asks the open tabs over BroadcastChannel `ch_auth` (message
  `need`; a signed-in tab answers `session`) and waits at most 400 ms (`CH_AUTH.settled()`; index.html and app/core.js wait
  for it before they choose between the app and the sign-in screen). No answer = signed out. Every sign-in, refresh and
  sign-out is broadcast (`session` / `signout`), so a sign-out in one tab signs out all tabs, and a different user
  signing in on one tab is followed by the others. Only one tab refreshes at a time (`navigator.locks`
  `ch_auth_refresh`); a tab that waited for the lock uses the session a peer already refreshed and makes no token call.
  A refused refresh first asks the peers once (400 ms) for a newer session before the tab signs out. Needs no env var.
  An old localStorage `ch_sb_session` is deleted at load and never used, so each user signs in once after this release.
  The offline queue (`ch_sync_queue`, IndexedDB), the per-user cache, `ch_last_user` and `ch_local_identity` are NOT
  touched on close: signed out = sync off, queued edits wait; the same user signing in again sends them once; a
  different user never sends them (`_entryBelongsTo`). Do not add any clear on pagehide/beforeunload. Limits: if the
  browser restores tabs on start (Chrome "Continue where you left off", Ctrl+Shift+T, Edge restore) it restores
  sessionStorage too and the user stays signed in; page code cannot stop that. The server-side refresh token stays valid
  until sign-out or revoke (Supabase Free has no inactivity limit; not checked in the dashboard); the client now keeps it
  only while a tab is open. How to check: node test-sync-golive-blockers.js ("8a:" to "8l:" tests); in DevTools
  Application, `ch_sb_session` is under Session Storage and absent from Local Storage; close all windows, open the site:
  the sign-in screen shows.
- A token refresh result belongs to the session it started from (app/ch-auth.js `_refresh`; the one check is
  `_sameStoredSession`: same user id and same refresh token in storage). The tab's session `ch_sb_session` is kept equal to
  the other tabs' by the broadcasts above. After the Supabase answer it is read again. If another tab changed it meanwhile (a different user signed
  in, or signed out) the result is dropped: nothing is saved, nothing is applied, and this tab follows the stored session
  (`chAuthStateChanged` fires, db.js bumps its identity epoch). A REFUSED refresh (400/401/403) also ends only the session
  it was for; a session another tab stored meanwhile is kept. How to check: node test-sync-golive-blockers.js, the four
  "7a:" tests (real ch-auth.js with a held token request).
- A 401 on a data write or on the queue drain: one token refresh, then the same request again (`CH_AUTH.withAuthRetry`,
  called from `_putWithAuth` in app/db.js, the one place a refused write is reported). The "server refused this sign-in"
  bar (`dbAuthRejected`) shows only when the final answer is still 401/403 and the session ended. If the refresh could not
  reach Supabase, the session is kept, the offline banner shows, and the write stays queued for the next drain.
  How to check: in DevTools Network, a PUT answered 401 is followed by a `/auth/v1/token` call and a second PUT (200);
  no red bar appears.

## 6. Sync write rules (app/db.js)

- No write before the first full pull (2026-10-21, branch 2026-10-21-sync-safety-client). In backend mode 'on', nothing
  goes to the server until `_hydrateInner` finished every read for the signed-in user (`_pulledUid`, rule
  `_hasFullPull`, app/db.js; public `DB.hasFullPull`). ONE gated send: `_sendKvPut` returns `held-no-pull` for every
  caller (live write, drain, merge-push inside the pull, first-connect upload, conflict resend) and each caller queues
  the value (`_enqueueWrite`). A merge-push made during a pull therefore waits until the whole pull is complete. The
  only bypass is the named flag `allowBeforeFullPull: true` in the payload, set by `restorePush` alone (an explicit
  user restore of one key at a known server version); it is never sent on the wire. A failed manifest, batch read,
  drift read, deletion-record read or an identity change leaves the gate shut. A successful pull releases the queue
  and fires the window event `dbFullPull` once per sign-in. `warmCache` waits for a pull when a READ failed
  (`_pullReadsFailed`): `_holdForFirstPull` retries after 1, 2, 4, 8 s, then every 15 s, so the page does not start on
  an empty cache; a browser that already holds data (`_cacheHasContent`) starts after 3 tries and retries in the
  background every 30 s (`_scheduleBackgroundPull`) and on `online`. A 401/403 answer (`_pullRefused`) ends the wait
  (the "server refused" banner shows). While it waits, each retry fires `dbOfflineBanner` with `waiting:true`; the
  existing small offline banner in app/sync-ui.js (`offlineBannerText`) then reads "Could not load <what failed> from
  the server. Nothing is saved until it loads. Retrying automatically." with the technical detail on hover. No new
  timer when sync is off. Check: node test-sync-golive-blockers.js (SYNC-SAFETY 1, 2, 5 tests).
- Queued write versus the pull (app/db.js `_queuedWriteBlocksPull`, `_resolveStaleQueuedWrites`). A queued write
  stops the pull from taking the server copy of its key only while the server version is not newer than the version
  the write was based on (`entry.baseVersion`; none recorded counts as older). A newer server copy wins: the write
  leaves the queue and goes to the normal conflict path (`_handleConflict`: list merge or the modal; local side
  archived). A held draft never blocks (see below). Only the signed-in user's OWN waiting write counts, for shared
  keys too (`_queuedEntryFor`, `_hasQueuedWrite`): another user's write never blocks or opens a conflict for this
  user. Check: SYNC-SAFETY 3 tests, IDENTITY 2.
- Held local draft (app/db.js `_holdLocalDraft`, app/sync-ui.js `_renderHeldDrafts`, `renderHeldLink`). "Decide later"
  (action `dismiss`), a closed modal, an unknown action or a missing modal keep the local value as a queue entry with
  `held:true`. The drain (`_drainQueueLocked`, `_queueHasSendable`) never sends it. It counts as an unsynced change
  but does NOT block the pull: the page shows the server copy (the old page value goes to Conflict history), the
  draft stays in the queue, and the pull does not ask again for a key that has a draft (`_findHeld` in the drift
  check). A normal edit of the key does not replace the draft (a newer held draft does). Small pill "Held drafts (N)"
  (id `ch-held-link`, bottom row) opens Sync status; there a collapsible "Held drafts (N)" lists each draft (what,
  when, which user). "Use my draft" = `DB.releaseHeldDraft(key)`: removes the draft and writes the value again with
  `set`/`remove` (normal gated path, based on the server version this device holds; a newer server copy opens the
  conflict choice again). "Discard" = `DB.discardHeldDraft(key)`: copied to Conflict history (reason
  `held-draft-discarded`) first. `DB.getHeldDrafts()` lists only the signed-in user's drafts. Check:
  node test-sync-golive-blockers.js (HELD 1-5 tests).
- Identity safety (2026-10-21, app/db.js). A queued, held or stale write made as user A is never sent as user B:
  `_sendKvPut` refuses an entry whose owner is not the signed-in user, the drain sends only own entries, every
  sign-in needs its own full pull (`_pulledUid` is reset in `_handleAuthIdentityChange`, so A returning after B must
  pull again before any send). `_clearPerUserLocalState` also removes from the page and the version map any shared
  key that holds another user's UNSENT edit (not held drafts); `_reapplyQueuedPerUserValues` puts it back, with
  `entry.baseVersion` as the stamp, when its author signs in again (a newer server copy then goes to the conflict
  choice for A). Before this, B saw A's unsent value on the page and a stale edit of A opened a conflict window for B
  with A's value. Check: IDENTITY 1-6 tests.
- Legacy utility blob (2026-10-21, app/utility-data.js), backend mode 'on' only (`_backendOn`); the GitHub site runs
  as before. `_legacyBlobToMigrate(customerId)` is the ONE rule for "copy the old `en_utility_<projectId>` blob into
  `en_utility_<customerId>`": the customer key does not exist at all (an existing blob, empty or not, is never
  replaced) and a project of that customer has a legacy blob with buildings. `_selfHealCustomersAndScope` applies it to
  already-healed projects; `saveUtilityData` never writes an empty auto-created blob (no load snapshot) while that rule
  finds a legacy copy. `loadUtilityData` writes nothing (no heal, no migration, no backfill) before the full pull
  (`_loadWritesAllowed`); it runs again, complete, on `dbFullPull` (`_loadWritesDeferred`). Check: SYNC-SAFETY 2 and 3
  utility tests.
- Signed-in name (2026-10-21, app/core.js, app/ch-auth.js). On the Netlify site, a page with a live session and no saved
  `ch_user` shows the session email (`CH_AUTH.sessionUser`); the GitHub site is unchanged. Check: SYNC-SAFETY 3 tests.
- A `DB.set` sends a PUT only when the canonical hash of the value differs from the hash stamped at the last sync
  (`_valueChanged`, one rule). Opening a pane or loading a page with no edit sends nothing.
- One PUT in flight per key (`_replicateWrite`). A write that arrives while one is in flight waits and is sent after
  the answer; the newest waiting value wins. Two PUTs for one key never overlap.
- How to check: open the browser DevTools Network tab on the sync host, filter `kv-sync`, reload the page and open the
  Building Performance and Savings Projection panes. Expected: zero PUT requests.
- Nothing is saved without a user edit: project progress is computed on read (app/core.js `projectProgress`, never
  stored on the Dashboard tab); recurring-meeting agendas and their tasks get ids from the project id and meeting date
  (app/csv-import.js `stableNumericId`), so two browsers generate one identical record; the Building Performance and
  Savings Projection panes save only from their inputs and buttons (`bpSave`, `bspSave`), never on open, and
  `getBspCfg` is the one reader of the Savings Projection settings with defaults. How to check: open a project
  Dashboard tab and both panes with the Network tab filtered on `kv-sync`: zero PUT.
  Same rule for zoom: opening the Equipment Matrix only reads `en_em_zoom` and paints it (`emApplyZoom`, app/equipment-matrix.js);
  only the zoom buttons save (`emSetZoom`). `setTableZoom` (app/site-functions.js) saves to local storage only on a click, not on a re-apply.
  Raw per-user keys (`RAW_PER_USER_LOCAL_KEYS`: `ch_theme`, `ch_settings`, view and order prefs) stay raw local keys, never sent to the server. On an identity change app/db.js `_clearPerUserLocalState(prevUid, nextUid)`
  parks the leaving user's values under the local key `ch_user_local::<userId>::<key>` (never in a backup: `isNeverBackupKey` lists the prefix) and puts back the next user's own values, so A keeps Light and the tip settings after sign-out/sign-in or A->B->A and B
  does not get A's. Quick Start seen flag `ch_qs_seen` and dismissed tips `ch_dismissed_tips` are not raw: app/tooltips-help.js reads and writes them with DB.get/DB.set (per-user, synced), and `chFirstVisit()` (app/tooltips-help.js) is the ONE first-sign-in rule: app shown, first server pull done (`DB.hasFullPull()`), `ch_qs_seen` not set; it sets the flag at once. `autoQuickStart` (overlay) and the tip bubbles (`_chShowFirstVisitTips`, `attachBaselineSaveTip`) both call it, so a later load shows neither; `chAuthStateChanged` resets the in-page latch. How to check: node test-quickstart-after-signin.js. How to check: node test-sync-golive-blockers.js (theme test), node test-em-zoom-no-write-on-open.js.
  Table prefs: the Cost Estimate table keeps column widths, hidden columns and a schema marker in `ch_tbl_*_pricing_tbl_<projectId>` (app/pricing-estimator.js).
  Render never writes them: `_pricingMigrateColSchema` returns when nothing is stored; `_pricingSetColWidths`/`_pricingSetHiddenCols` (user resize/hide/show only) also stamp the schema marker.
  How to check: node test-pricing-tblprefs-no-write-on-render.js (6 pass); Network tab, filter `kv-sync`, open JOCO Cost Estimate: zero PUT.
  Phase over allowance is a data notice: `console.warn` (not error) in `_pricingComputeRecommendedTimeline`.

## 6d. Backup importer: scripts/migrate-seed.js (Matt runs it; agents never hold the key)

What it is: a Node script (scripts/migrate-seed.js) that loads a backup file into the Supabase `kv` table and the `pdf_blobs`
bucket. It talks to Supabase directly, so it costs 0 Netlify credits and works while Netlify has no deploy credits.
The old whole-key `--force`, `--live` and `--dry-run` flags are gone. Merge rule: it calls `RestoreMerge.mergeValue(key,
server, backup, 'newer-wins')` (app/restore-merge.js), the same function as Restore "Merge, keep whichever copy is newer". A
record only on the server stays. A record in both is replaced by the backup record whole in the importer only (it passes `{ replaceWhole: true }` as the sixth argument of `mergeValue`; app Restore does not, and keeps every field the backup lacks) (a field only the server record has, such as a stale `updatedAt`, is dropped; the nested list and the derived meter cache fields are kept; the old value goes to `kv_history`; the dry run counts it as changed and the diff file names the lost fields). On top: a backup record is dropped when the server
copy has a strictly newer `updatedAt`/`updated_at`/`modifiedAt`/`lastModified`. No timestamp = the backup wins. This
"newer wins" rule lives INSIDE `mergeValue` (app/restore-merge.js, `recordTime`/`curIsNewer`, 'newer-wins' mode only; 'backup-wins' is an unconditional overwrite that lists the newer server records it overwrites). It runs at
every level (building, meter, bill, pricing entry, plain-key object). The app Restore "Merge, keep whichever copy is newer" uses the
same function, so the app and the importer give the same result, except that the importer replaces a matched record whole. A key is HELD (no write, listed in the diff file) when the
server has a whole item the backup lacks: a list item, a map entry, or a plain field of any type in a plain-key object. A field lost inside a matched record is not a hold (see above). Name a held key in `--allow-removal`
to write it.

Modes:
- Default = dry run. No write. Console shows counts only (keys and records: new / changed / server-only / identical). The full
  diff (record ids, every record the backup overwrites) goes to `<report-dir>/YYYY-MM-DD-HHMM-supabase-import-diff.json`
  (default `AI/_context/live-data/diffs/`). The diff names nested records (level + id path), the field names that change, are
  added or are lost, and why a key is held. Field names only, never values. The script refuses any report or snapshot folder inside the repo.
- Server for the diff: `--server-file <image.json>` (offline, no key) or `--target prod|staging` (GET only).
- `--apply --target prod|staging` writes. Order: read server rows, save them to
  `AI/_context/live-data/snapshots/YYYY-MM-DD-HHMM-supabase-snapshot.json` (stop if that fails), then per key one `kv_history`
  row (the old server row) and a version-checked PATCH (a key that changed on the server meanwhile is reported as a conflict,
  never overwritten), then new keys at version 1, then PDFs (write-once, same-hash re-run is a no-op).
- Target safety. Needs ONLY the target-specific values: URL = env `SUPABASE_URL_PROD` or `SUPABASE_URL_STAGING`; key = env
  `SUPABASE_SECRET_KEY_PROD` / `SUPABASE_SECRET_KEY_STAGING`, else the Windows Credential Manager generic credential
  `companyhub-supabase-<target>-key`. The generic `SUPABASE_URL` and `SUPABASE_SECRET_KEY` are NEVER read. There is no `--url` and no
  `--cred-target`. A missing value stops the run (resolveCreds, scripts/migrate-seed.js). A URL ending in `/rest/v1/` is cut to the bare origin (normalizeSupabaseUrl). The PDF stat treats HTTP 404, and HTTP 400 with a Storage body of statusCode 404 (NoSuchKey), as missing; any other 400 stops the run (pdfStorageStat). The log prints the target name and the host
  (`Server: WRITING to target=prod host=<host>`), never the key. No prompt. The key is never printed or stored.
- `kv_history` rows written here are not trimmed (kv-sync.js trims on its own writes: 20 rows or 30 days a key).
- Failed writes (applyPlan, applyPdfFiles, fetchWithRetry, scripts/migrate-seed.js). Each kv, kv_history and PDF write is tried up to 4 times (RETRY.attempts) with 1 s, 2 s, 4 s waits and a 180 s timeout per try. The same timeout and retry apply to the reads (kv row read, key list, Storage stat and download), so a hung read cannot stop the run silently. Retried: a network error, a timeout, HTTP 408, 429, 500, 502, 503, 504 and 520-524 (isRetryableStatus). Any other status (a 4xx, 501, 505) is not retried. A retry that gets 409 with the same hash on the server counts as inserted (the first try wrote the row and lost the answer); if the re-read itself fails, the FAILED line says so. A PATCH that matches 0 rows, or gets a 2xx answer that is not JSON, reads the key: the same hash on the server counts as updated (patchKvRow); a different hash is `conflict-version-changed`. The history snapshot is idempotent: before the write and before every retry the importer looks for a kv_history row with the same key and version (historyRowExists) and writes none if one exists, so a lost answer or a re-run after a failed PATCH adds no duplicate row. kv_history has no unique constraint; no schema change was made. A write that still fails is listed by name: `FAILED key <key> status=error http=<status> reason=<server message>` (or `FAILED pdf <canonical key> ...`). The key name and a shortened server error are printed (scrubServerText: the error code and the first 80 characters of the message). The secret key is never printed. A server error can quote a fragment of the row, so the cut is to 80 characters; it is not a guarantee that no data text can appear. Conflicts and history failures are listed too. If N > 0 the last line is `APPLY INCOMPLETE: N failed` and the process exits with code 1; `APPLY COMPLETE` prints only when 0 failed. If keys were HELD (not written) the last line is `APPLY COMPLETE WITH N HELD key(s) NOT WRITTEN` and the re-run will still show them as changed. Run the same command again: it writes only what is missing. A kv value over KV_VALUE_MAX_BYTES (25 MiB of JSON) is shown as `OVERSIZE` in the dry run and is not sent by --apply (it fails by name). That limit is an importer guard, not a Supabase number: the largest value proven to write is the 9 MB Equipment Matrix key. The app reads and writes that value through netlify/functions/kv-sync.js, which gzips bodies to stay under Netlify's ~6 MB function cap (comments at kv-sync.js:44-48 and 178-181, measured 2026-07-19: 9.03 MB to about 0.35 MB), so a large importer value does not need a smaller limit for the app. An empty backup value (`empty-skipped`) adds 0 to the record counts.
How to check: `node test-migrate-seed.js` (38 tests, in-memory fake Supabase, no network). Then the same command without
`--apply` must show 0 new and 0 changed.

## One month rule: billMonth (2026-10-13, branch 2026-10-13-phase3-quick-annual-entry)
- What: `billMonth(bill, meterBills)` (computations/normalization.js) is the one answer to "which calendar month does this whole bill belong to". ## Automatic repair of stored bills from their PDF page (2026-10-15, branch 2026-10-15-auto-repair)

- What: a background pass re-reads the stored PDF page of each bill that has a flag or a misread, and of the bills next to it, and repairs the bill from the fresh read. Entry: `scheduleAutoRepair` (app/auto-repair.js), called at the end of the read-chain block of `loadUtilityData` (app/utility-data.js). It runs in the user's browser (no time zone, no server, no env var, no Netlify call). Audit notes use `reasonLabel()` (computations/bill-repair.js), the one place a reason becomes plain words; stored markers keep the raw reason. The fallback `showToast` (app/site-functions.js) sets `#toastMsg`, keeps the X button and ignores a stored `ch_toast_duration` of 0 or less (third argument `0` = stays until X). How to check: node test-onload-toast.js.
- Which bills (`repairEligibleBills`, computations/bill-repair.js): a bill with a pdfKey and no marker for the current `EXTRACTOR_RULES_VERSION` (app/energy-savings.js, next to `_pickFileRule`) that has a counted flag (`BILL_COUNTED_FLAG_RULES`), a read-chain flag (`read_continuity`, `read_rollback`, `read_usage_mismatch`), blank reads or reads that do not add up (electric), or is the bill before or after one of those. Two markers carry no `v` and are tried again on a later load: `{ status: 'waiting', reason: 'the PDF is not on this browser' }` (once per load, until the PDF is restored) and `{ status: 'error', reason, tries }` (a read that threw; after `AUTO_REPAIR_MAX_TRIES` = 3 loads the bill is declined for the version with "N tries" in the reason). `dup: true` on a marker means the row is one of a duplicate group; alone it carries no version. The work list is built ONCE per run (one `repairEligibleBills` per meter), then only the meters a PDF touched are listed again. Meter objects are looked up by id again after every `await` (a reload or restore during a read replaces `utilityData`; the write goes to the live objects). Written after each PDF and saved with `saveUtilityData(customer)`, so a closed tab loses at most the PDF in progress and the next load continues. The pass runs only when `DB.isReady()` (the IndexedDB-backed store); otherwise it logs `the storage is not ready` and waits for the next load.

## Baseline rates are usage-weighted; mismatched bills are left out (2026-10-13)

- Browser only. No schedule, no timer, no env var, no server call. Cost: about 0.7 ms per `computeSeasonalBldgRates` call (runs the flag engine once per meter, no cache); `getProjMatrixSavingsTotal` for all 5 projects 48 ms on the 2026-10-12 backup.
- Method (`computeSeasonalBldgRates`, computations/rates.js): every derived baseline rate (kWh, kW, therm, gallon, water, sewer, stormwater; per season, per calendar month, annual) = sum of the charges / sum of the usage over the bills in that bucket. It is NOT the mean of per-bill rates. Charge and usage of one bill come from `getBillRateParts(bill, type)` (rates.js), the same function `getStoredRate` and `getStoredKwRate` divide. A straddling Evergy bill with printed split lines gives each season its line rate weighted by that line quantity (`_billSeasonRates` returns `summerQty` / `winterQty`: kWh of the lines, or kW = charge / rate). A straddling bill without split lines gives its usage prorated by its days in each season. A bill with a stored rate but no cost or no usage has no weight and gives nothing. ## Meter read repair (2026-10-14)

- What: one rule repairs a start read, end read or read difference the PDF reader misread, using the previous bill's end read and the next bill's start read on the same meter. `computeReadCorrection` (computations/bill-flags.js, search the name). Evidence principle: a value is evidence only when the check that confirms it would fail for every 1- or 2-digit misread of that value. Reads compare within one unit of the coarsest last printed digit (print rounding can make two printed values that should agree differ by one unit; the read_continuity tolerance is not used), and a correction must move a field by more than that one unit, so a one-unit difference is never changed. The read difference D is proven by the usage (`_rcUsageProves`) only when |D x M - U| <= half a unit of the usage's last printed digit AND that residual plus half a usage unit is smaller than one unit of D's last printed digit times M. D and U are NOT independent: the PDF reader rewrites D = E - S and U = D x M, and a misread can store D and U both misread but consistent. So a change of the end read (c) or of the read difference (d) needs the next bill's start read; without it both decline. On-peak + off-peak kWh are not evidence (their sum differs from the billed kWh by up to about 1 kWh on actual bills; one D step is 0.016 kWh at multiplier 160). Cases, D proven: a, both reads off by the same amount, next bill's start = previous end + D; a0, the same on the NEWEST bill (no next bill), provisional: identical offset in both reads, each a 1- or 2-digit misread, start read >= 10 x D (a replaced meter starts near zero), the previous bill clean (its span = its D, its D proven by its usage) and the shift DOWN past the previous bill's start read (otherwise the previous bill's end read could be the misread; a shift up or a smaller shift waits for the next bill); b, only the start wrong (end - previous end = D; next start, if present, = end); c, only the end wrong (start = previous end, next start = start + D). D not proven: d, start = previous end and next start = end, so the READ DIFFERENCE becomes end - start (must agree with the usage within half a unit). Any other mix, a read difference printed coarser than the reads, a bill without the needed next bill: no change, the flag stays. A value changes only when the new and old text have the same length and differ in at most 2 characters. Self-check (`_rcRevertProvisional`): on every walk, an a0 correction whose bill now has a linked next bill with a start read is kept (its records become rule-a records) when that start read equals the corrected end read and reverted (reader values back from the records, records removed, read_continuity flag on) when it does not. A bill links to the previous one only when it starts 0 to GAP_DAYS days after it (a duplicate or overlapping bill never links); extracted bills are walked in date order. A meter change, a rollover, a multiplier change, an estimated bill or a gap is never changed. User wins: a bill with a corrected field the user changed afterwards, or a field in `_userCorrected`, is skipped; every edit path (saveBillRow, submitValueCorrection, updateBillField in app/csv-import.js, the Review Bill Corrections apply in app/bill-corrections-review.js, both stores, single and bulk) calls `clearReadCorrectionRecords`, which removes the record and stamps `_userCorrected`.
- Callers: `correctMeterReadChain(meter)` for every meter in `loadUtilityData` (app/utility-data.js, runs on every page load, in the user's browser, no time zone, no timer). It saves through `saveUtilityData(SAVE_ALL_PROJECTS)` only when it changed a bill, and a second load changes nothing. `correctExtractedReadChain` in the PDF read-chain step (app/bill-analysis.js, runs per PDF with 2 or more bills). `readCorrectionMarkers` copies the record to every saved-bill builder.
- Original kept: `_auto_corrected_startRead` / `_auto_corrected_endRead` / `_auto_corrected_readDifference` = `{ original, corrected, reason }` on the stored bill (capitalized names on an extracted bill). The Bills table does not mark the cell; the record shows in the Edit Billing Period "Change history" section (since 2026-10-14 there is no banner, no diamond mark and no cell tint; the flag reason list `.bill-banner-list` is capped at 120px with its own scroll in energy-department.html). A record whose corrected value no longer matches the cell is not drawn.
- Speed: `_rcWalk` (computations/bill-flags.js) skips a bill that has no correction record and whose start read equals the previous end read and whose end read minus start read equals its read difference, both within print rounding (`_rcCleanLink`); each read is parsed once per walk. Measured with `500 meters x 60 bills`: about 450 ms before, about 100 ms after, per load.
- Needs: no env var, no network, no schedule. Console line on a repair: `[read-chain correction] Repaired the meter reads of N bill(s)`.
- Check: `node tools/gate-read-chain-correction.js` (about 40 s; in the regression gate). Property tests over 9 multipliers, 4 read precisions, 5 usage precisions, with and without a next bill: every 1- and 2-digit substitution of every read field (about 1.5 million cases), both reads shifted by the same misread offset (about 620,000), the read difference misread with the usage recomputed from it (about 307,000; the real correlated bill), and about 1.6 million real meter replacements with no next bill (a replacement that starts under ten read differences is never changed; refurbished-meter coincidences at or above are counted and printed, the self-check reverts them). It fails if a correct field is ever changed or a changed field is not the true value; plus the scenario cases (a, a0, b, c, d, the previous bill's end read misread with its D and usage rewritten, one-unit print rounding, coarse usage, two culprits, meter replacement, multiplier change, duplicate, out of order, estimated, gap, overlap, rollover, user edit, edit-path clear, extraction order, self-check confirm and contradict, banner markup and CSS). To check by eye: open a meter with a repaired bill on the Bills tab and click the mark.

## Printed read check (2026-10-14)

- What: the PDF reader keeps a printed read difference and a printed kWh exactly as extracted (app/bill-analysis.js, Step 1 and Step 2 of the read chain, and the recovery pass). It computes end read minus start read, or read difference times multiplier, only when the PDF printed no value. The arithmetic is a CHECK: `computePrintedReadMismatch` (computations/bill-flags.js, the only copy). Tolerance is the print precision: reads and the difference may differ by one unit of the coarsest last digit; the kWh may differ from difference times multiplier by half a unit of its last digit plus half a unit of the difference's last digit times the multiplier, plus (when the multiplier prints decimals) half a unit of the multiplier's last digit times the difference. Decimals are counted on the number only (`12.00CR`, `(12.00)` and `12.00 kWh` have 2). A rollover (end under start) is checked only when the reader saw the meter's dial limit (`b._meterRollover.boundary`, set by the Step 1 rollover branch whether or not the difference was printed): the expected difference is limit + 1 - start + end. The rollover branch keeps a printed difference and computes only a missing one.

## kv_history on every write (2026-10-21)
- What: kv-sync.js `handlePut` (snapshot call at kv-sync.js:335, `shouldSnapshot` :380, `snapshotHistory` :387, `enforceHistoryRetention` after). Every PUT that changes a key (normal, tombstone, explicit overwrite) writes the previous row (key, value, version, updated_by, replaced_at) to `kv_history` BEFORE the PATCH. No row when the new value equals the old (hash compare), none for a new key, none for a stale-version PUT (409). One row per key+version (looked up first). If the history insert fails the PUT returns 502 and the row is not changed. PostgREST has no multi-statement transaction, so this is snapshot-then-CAS; a lost CAS leaves at most one extra row for the version still current.
- Why: on 2026-10-21 three keys were rewritten by normal PUTs with no saved old copy.

The "over 1 MB" test uses UTF-8 bytes (`Buffer.byteLength`), not characters. The trim (2-3 Supabase requests) runs only in a request that inserted a history row; a write with no snapshot (new key, equal value, snapshot row already there) makes no trim request, to save Netlify compute. No schema change and no migration (kv_history columns are unchanged).

## Automatic weather refresh (2026-10-27, branch fix/2026-10-27-weather-refresh)
- What: monthly HDD, CDD and average temperature (stored per ZIP in DB key `en_wdd_<zip>`, rows `{ym, hdd, cdd, avgTemp}`) fill themselves. The one owner is computations/weather-refresh.js (`wxRefreshZip`, `wxMergeAppend`, `wxFetchRows`). The browser calls `api.weatherdatadepot.com` directly (it answers `access-control-allow-origin: *`; tested from a page origin, HTTP 200). No Netlify function, no timer, no schedule, 0 Netlify invocations. CSP `connect-src` of energy-department.html lists the host.
- When: `wddRefreshProjectWeather(projId)` (app/utility-data.js) runs from ONE place, `udSelectBldg` (a building opens). It takes every distinct 5-digit ZIP of the project's buildings plus the project ZIP. A ZIP is fetched when it has no stored month or its newest stored month is older than last calendar month (local time of the browser). Once per ZIP per page load. A failed fetch is silent (stored months stay).
- Rules: stored months are never changed; only months newer than the newest stored month are appended (frozen baseline months cannot move). The current calendar month is never saved. A month missing from any of the 3 source series stays absent (never 0). A ZIP with no stored month gets all months from 2020. HDD and CDD come as running yearly totals (balance point 60 F); a month is the total minus the month before; a month whose predecessor is missing is left out. Average temperature is already monthly.
- Reports: `collectWeatherData` (app/csv-import.js) gives `null` (not 0) for a month with no weather row. The Weather appendix table (`rptPageAppendixWeather`) prints "No weather data" and the weather chart (`_apbWeatherHddCddChartSVG`, fed by `rptPageAppendixBaseline`) prints "No weather data" with no bars. The regression calculation table in `rptPageAppendixBaseline` also prints "No weather data" (no predicted or saved value) for a month with no weather row.
